## What is currently stored

- The repository already includes `backend/data/fixtures/ncrb_delhi_city_women_crimes.json`: five NCRB Delhi City metropolitan yearly aggregate totals (2020–2024). It is explicitly not locality-level or route-level evidence. It was not newly imported by this work. Its source metadata references NCRB table URLs and an OpenCity mirror; the OGD catalog resources checked above are not the direct origin of this fixture.
- Four source-linked locality/landmark news candidates were imported to the local SQLite DB: CR Park (near Kalka Public School), Jheel Park near Welcome, Shalimar Bagh (locality only), and Tajpur Pahadi/Badarpur. They are all `reported` and `needs_review`; there are four source URLs and four place observations, zero incident coordinates, and zero accepted incident-to-segment matches. No victim names, exact addresses, or full article text are stored. A date inferred from article phrasing is documented in the source evidence notes.
- A bounded OSM pilot GeoJSON was retrieved from the original OSM map API and imported to SQLite: six windows around CR Park, Welcome Metro, Shalimar Bagh, Tajpur Pahadi/Badarpur, Moolchand/Lajpat Nagar, and Majnu Ka Tila; 1,362 OSM ways with pedestrian-related `highway` tags. OSM API responses did not provide a snapshot timestamp; collection date is 29 Oct 2026 and is not a canonical OSM version. The source is ODbL with attribution `Â© OpenStreetMap contributors`.
- No authoritative locality boundary, licensed Safetipin audit points, complete Delhi pedestrian graph, or accepted incident-to-segment matches were imported. OSM walkability tags are map labels, not field confirmation of sidewalks/accessibility.
- Therefore the route safety estimate remains deliberately `not_supported`; route order is unchanged. The planner shows source-linked candidate reports only when selected origin/destination text exactly names their locality/landmark, and shows tagged OSM map context only within the pilot windows. Neither constitutes a route risk score or street-level incident match.

## Implemented ingestion foundation

SQLite initialization now creates separate provenance-oriented structures for normalized incident events, multiple source links and evidence spans, role-specific place observations with uncertainty/privacy/review status, licensed pedestrian-network versions, walkable segments, reviewed incident-segment matches, and repeatable import-run status. Existing aggregate `official_stats` and ML candidate extraction remain separate. No routine automatically geocodes user-provided incident text or snaps locality-only observations to streets.

`GET /api/v1/routes/safety-data-status` reports coverage. `POST /api/v1/routes/locality-reports` returns source-reported items whose locality/landmark exactly matches a comma-separated place label; it explicitly does not claim route proximity. `GET /api/v1/map/pedestrian-network?bbox=west,south,east,north` serves pilot OSM GeoJSON from the backend database for small extents. The Route Planner overlays these ways and displays source-linked candidate reports separately. `POST /api/v1/routes/walking` runs one shortest-distance path on connected pilot ways, snaps endpoints only within 150 m, and estimates time at 1.2 m/s. It refuses routes outside/disconnected from pilot coverage instead of falling back to driving directions. `risk_estimate` remains `not_supported`; no API ranks routes using the pilot data.

1. Obtain usable official annual tables/source files and confirm table definitions; the OGD catalog publishes under Government Open Data License-India, but downloadable table bytes should be verified before importing.
2. Ask Safetipin/GNCTD for explicit rights and a machine-readable export if audit observations are to be mapped.
3. Expand the OSM extract only after review of its coverage; preserve the limited-window note, retrieve an independently timestamped snapshot, retain ODbL attribution/version, and construct/validate a pedestrian graph (the current configured OSRM adapter is driving-mode and must not be reused as a pedestrian network).
4. Establish human review and privacy rules for news-event curation, then store only minimal redacted details with evidence references. Verify each candidate article and deduplicate follow-ups before marking a record reviewed.
5. Until those prerequisites are met, keep locality/segment risk in “Insufficient data”; do not extrapolate aggregate statistics or represent audit summaries as current street conditions.
