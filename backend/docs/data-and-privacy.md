# Data, provenance, and privacy

Use Delhi NCT records only. Official-statistics imports must explicitly mark each row with geography_scope=delhi_nct; recognized NCR names outside Delhi are rejected. Preserve source geography: district/metropolitan totals must not be mapped to localities. Each source needs name, permission basis, and geographic precision, plus optional reference, retrieval timestamp, version, and permitted-use notes. News requires a lawful-use basis and article reference; store only minimum permitted excerpts and no victim identities. Basic phone/email redaction runs on excerpts, but review sensitive input before ingestion.

Official and news-derived records use separate tables and trend series. Article counts reflect coverage and editorial selection, not crime incidence. Incident date is nullable and distinct from publication date. Missing data means unavailable, not zero. The bundled NCRB Delhi City dataset contains aggregate metropolitan-city registered-case totals for 2020–2024 with table references in `data/fixtures/ncrb_delhi_city_women_crimes.json`; it is not a locality-level dataset and must not be mapped to localities. NCRB notes that cities should not be compared purely on case counts. The 2024 report spans the IPC-to-BNS transition, so year-to-year comparisons need care. No locality gazetteer, boundaries, audits, weather, or traffic records are bundled.

Community reports are marked unverified, sanitized, and expiry-filtered. Precise location should not be submitted in community reports. Route location text is sent to the configured geocoding service (public Nominatim by default), and resolved coordinates are sent to the configured routing service. Use a self-hosted/contracted geocoder if public transmission is not acceptable. Signed-in journeys store the selected route and planned/start/completion times. Optional GPS display points are stored in the browser's session storage for map display and are not uploaded or added to account history.

The safety center creates a random 256-bit browser key and sends it as a bearer token to protect guest-workspace contacts, share controls, and SOS history. Signed-in account contacts use account sessions. Account passwords are stored as salted PBKDF2 hashes; session-token hashes, profile information, contact names/phone numbers, and selected journeys are stored in SQLite. Contact and journey records are account-scoped but are not encrypted at rest. New account sessions use an `HttpOnly`, `SameSite=Lax` cookie with `Secure` enabled for HTTPS; the frontend migrates a valid legacy bearer token to that cookie and then removes it from local storage. Clearing site cookies signs the user out. A location share stores one exact coordinate snapshot; its public link is a bearer secret, works for at most 60 minutes from the UI, and can be revoked by the creating browser. Recipients can view the location until expiry or revocation. Expired/revoked shares are deleted as safety API requests run. SOS events contain no location and expire after 24 hours. NAVIRA only records an SOS event; it does not call emergency services or send notifications. The user must complete calls or messages from their device.

Use persistent storage and an appropriate privacy/retention policy before relying on these records. The Render free blueprint uses an ephemeral filesystem, so accounts, contacts, journeys, active share records, SOS history, and model artifacts can be lost when the service restarts or redeploys.
